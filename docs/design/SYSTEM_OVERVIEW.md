# Agent 系统核心设计概览

## 一、Agent 入口路由与运行时框架

**核心问题**：业务咨询、固定流程、数据查询和复杂推理混在同一入口

**解决方案**：四层分类处理

1. **规则命中**
   - 空输入、无意义输入直接拦截
   - 确认续接场景识别
   - 0 次 LLM 调用

2. **模板回复**
   - 问候、自我介绍、能力清单等固定场景
   - 直接返回预设模板
   - 0 次 LLM 调用

3. **意图识别**
   - 模型进行语义分类
   - 后端能力策略映射
   - 1 次 LLM 调用

4. **多步推理**
   - 复杂请求进入 ReAct 循环
   - 模型规划工具调用
   - N 次 LLM 调用

**核心价值**：规则和模板类请求不进入 Agent 循环，复杂请求再调用模型和工具，降低无效 LLM 调用

## 二、结构化协议与上下文管理

**核心问题**：模型输出不可控，上下文难以追踪和回放

**解决方案**：Pydantic v2 定义数据契约 + 运行时状态管理

### 2.1 结构化协议

使用 Pydantic v2 定义 Agent 内部数据契约，将模型动作限制为四类：

1. **调用工具** (call_tool)
   - 指定工具名称和参数
   - 后端校验工具白名单和参数完整性

2. **答复** (answer)
   - 提供最终答案
   - 校验是否需要证据支撑

3. **反问** (ask_user)
   - 向用户追问信息
   - 补充缺失的必填槽位

4. **转人工** (handoff)
   - 超出能力范围转人工
   - 记录转人工原因

### 2.2 上下文管理

运行时维护完整的上下文状态：

1. **route**：路由决策信息
   - 意图分类结果
   - 能力策略映射
   - 工具白名单和风险等级

2. **tool trace**：工具调用轨迹
   - 工具名称、参数、结果
   - 执行时间和状态
   - 失败原因

3. **evidence**：证据来源
   - 检索到的文档片段
   - 来源文档和位置
   - 相关性评分

4. **model decision**：模型决策过程
   - 每步推理的输入输出
   - 动作类型和参数
   - 校验结果

5. **会话状态**：多轮对话上下文
   - 用户画像和历史
   - pending_action 状态
   - 槽位填充进度

### 2.3 异常处理

处理各类异常情况，保证系统可控：

1. **重复调用**
   - 检测同名同参数的重复工具调用
   - 超过阈值返回 invalid_action

2. **缺少证据**
   - 知识问答场景校验是否有检索结果
   - 无证据不允许回答

3. **工具失败**
   - 转为结构化 ToolResult
   - 不抛异常穿透主循环

**核心价值**：多轮上下文可追踪、可回放，便于问题排查和系统优化

## 三、工具权限与两阶段确认

**核心问题**：状态变更操作风险高，需要严格的权限控制和确认机制

**解决方案**：业务能力策略 + pending action 两阶段确认

### 3.1 业务能力策略

按场景声明执行边界：

1. **工具白名单**
   - 每个能力明确允许调用的工具
   - 模型不能自创工具权限

2. **必填槽位**
   - 定义业务必需的参数
   - 缺失时自动追问

3. **风险等级**
   - low：只读查询，直接执行
   - medium：数据修改，需要确认
   - high：资金操作，严格确认

4. **步数上限**
   - 限制 ReAct 最大循环次数
   - 防止模型无限循环

### 3.2 两阶段确认机制

状态变更类工具的执行流程：

**阶段一：生成 pending action**
1. 模型提出工具调用
2. 后端识别为高风险操作
3. 生成 pending action，保存：
   - 工具名称和参数
   - 槽位快照（企业名、产品名等关键信息）
   - 前置条件哈希（业务状态）
   - 过期时间
4. 返回确认文案给用户

**阶段二：校验后执行**
1. 用户确认
2. 校验会话快照：
   - session_id 一致性
   - 槽位快照未变化
   - 前置条件哈希未变化
   - 未过期
3. 校验通过后执行真实业务动作
4. 校验失败则拒绝执行

**核心价值**：避免确认前执行真实业务动作，防止 TOCTOU 攻击

## 四、多策略切片与 Hybrid RAG

**核心问题**：政策文档、PDF 指南和表格规则混合导致的漏召问题

**解决方案**：按文档类型路由切片 + 双路召回融合

### 4.1 多策略切片

按文档类型实现差异化切片：

1. **Markdown 文档**
   - 保留标题路径（h1 > h2 > h3）
   - 维护文档结构信息
   - 便于定位具体章节

2. **PDF 文档**
   - 过滤页眉页脚
   - 去除无关格式信息
   - 保留正文内容

3. **表格规则**
   - 按列头展开
   - 每行转为独立文本
   - 保留表格上下文

### 4.2 Hybrid RAG 双路召回

结合向量检索和全文检索：

**路径一：向量召回**
- 使用 BGE-M3 模型
- 适合语义相似问题
- 召回 Top-K 候选

**路径二：全文检索**
- 使用 PostgreSQL 全文检索
- 适合编码、关键词查询
- 召回 Top-K 候选

**融合策略：RRF (Reciprocal Rank Fusion)**
- 合并两路召回结果
- 按排名倒数加权
- 兼顾语义和精确匹配

**核心价值**：提高召回率，兼顾语义问题和编码/关键词查询

## 五、评测、观测与扩展机制

**核心问题**：系统质量难以量化，问题难以排查，能力难以扩展

**解决方案**：多维度评测 + 全链路 trace + 统一扩展接口

### 5.1 多维度评测指标

建设完整的评测体系：

1. **检索维度**
   - 召回率 (Recall)
   - 准确率 (Precision)
   - MRR (Mean Reciprocal Rank)
   - NDCG (Normalized Discounted Cumulative Gain)

2. **答案维度**
   - 准确性（与标准答案对比）
   - 完整性（是否遗漏关键信息）
   - 相关性（是否回答了用户问题）
   - 幻觉率（是否编造信息）

3. **业务维度**
   - 任务完成率
   - 用户满意度
   - 转人工率
   - 错误率

4. **成本维度**
   - Token 消耗
   - LLM 调用次数
   - 平均成本

5. **性能维度**
   - 端到端延迟
   - 各环节耗时分布
   - P50/P95/P99 延迟

### 5.2 全链路 Trace

记录完整的执行过程：

1. **路由 trace**
   - 规则守卫结果
   - 场景直达匹配
   - 模型路由输出
   - 能力策略映射

2. **工具调用 trace**
   - 工具名称和参数
   - 执行时间和结果
   - 失败原因
   - 重试次数

3. **RAG 召回 trace**
   - 查询改写结果
   - 向量召回结果
   - 全文检索结果
   - RRF 融合结果
   - 最终使用的文档片段

### 5.3 扩展机制

统一的扩展接口：

**MCP 工具调用层**
- 接入外部工具
- 统一适配为 BusinessStatus / ToolResult
- 支持工具注册和发现

**Skill 文档索引**
- 按场景加载业务知识
- 动态扩展知识库
- 支持多租户隔离

**统一数据格式**
1. **BusinessStatus**
   - 业务状态码
   - 业务数据
   - 错误信息

2. **ToolResult**
   - 执行状态（SUCCESS / FAILED / TIMEOUT）
   - 返回数据
   - 是否 terminal（可以结束循环）

**核心价值**：系统质量可量化、问题可排查、能力可扩展

## 七、核心设计价值总结

1. **效率优化**：四层分类处理，降低 60-70% 的无效 LLM 调用
2. **安全可控**：结构化协议 + 能力策略 + 两阶段确认，确保系统行为可预测
3. **质量保障**：Hybrid RAG 提高召回率，证据驱动回答降低幻觉率
4. **可观测性**：全链路 trace + 多维度评测，问题可排查、质量可量化
5. **可扩展性**：统一的工具接口和文档索引，能力可快速扩展
