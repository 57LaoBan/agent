## 2. A 类：模型缓存与启动问题

### A1. `cache_dir` 默认路径错误，导致重新下 2.3GB 模型

**现象**：跑离线入库脚本时 `pytorch_model.bin` 在下载，速率 342MB/s，要等 6 秒下完。但 checklist 明确说"模型已在本地"。

**根因（用 Java 类比）**：
- 你的"Maven 本地仓库"在 `~/.m2/repository`；
- 我代码里把"仓库根"配成了 `~/.m2`（少了一层 `repository`）；
- Sentence-Transformers 库去 `~/.m2` 下找 `models--BAAI--bge-m3`，找不到，触发"重新拉取"。

实际的 HuggingFace 缓存目录结构是：

```text
~/.cache/huggingface/hub/         ← 真正的缓存根（类比 ~/.m2/repository）
  models--BAAI--bge-m3/
    snapshots/<sha>/
      pytorch_model.bin           ← 已存在，2165 MB
      tokenizer.json
      ...
```

但代码里 `cache_dir` 默认写的是 `~/.cache/huggingface`（少一层 `hub`）：

```@d:\companyCode\agent\src\xinyidai_agent\rag\embedder.py:27
        cache_dir: str = r"C:\Users\阿猫\.cache\huggingface",
```

**修复**：把默认值改为 `None`，让 sentence-transformers 走自己的标准路径（自动找到 `…/hub`）。这等于在 Java 里"不写 `<localRepository>`，用 Maven 默认的 `~/.m2/repository`"。

修复落点：`@d:\companyCode\agent\src\xinyidai_agent\rag\embedder.py:24-46`、`@d:\companyCode\agent\src\xinyidai_agent\rag\reranker.py:19-50`

### A2. 首次请求冷启动 30 秒（CPU 加载 BGE-M3）

**现象**：第一次发 query 等了 29 秒；第二次降到 190 ms。

**根因**：
- BGE-M3 是 ~2.3GB 的深度学习模型；
- 第一次调用 `embedder.embed_query("xxx")` 才触发"懒加载"——把权重从硬盘读进内存、做一次推理；
- 类比 Java：相当于 Spring `@Lazy` 的 Bean 在第一次使用时才初始化。

**修复**：在 FastAPI 启动时**异步预热**，类比 Spring 的 `ApplicationRunner`：

```python
# @d:\companyCode\agent\src\xinyidai_agent\rag\factory.py:144-155
def _schedule_warmup(runtime: AsyncRuntime, embedder: BGEEmbedder) -> None:
    """fire-and-forget：把首次模型加载放到后台 loop，不阻塞启动。"""
    async def _warmup() -> None:
        try:
            await asyncio.to_thread(embedder.embed_query, "warmup")
        except Exception:
            pass  # 预热失败不影响线上链路
    asyncio.run_coroutine_threadsafe(_warmup(), runtime.loop)
```

效果：服务启动后约 30 秒内，BGE-M3 在后台完成加载；首请求一般已经热了，体验跟 Java 应用启动后第一次请求 JIT 编译完成是一个意思。

## 3. B 类：数据库 / 连接池问题

### B1. 连接池缺 acquire timeout 与健康检查（**生产级隐患**）

**现象**：早期审查代码就指出过；本次没触发但已修一部分。

**根因（Java 对照）**：
- 你用 HikariCP 时会配 `connectionTimeout`、`validationQuery`、`idleTimeout`；
- 这个项目自己写了一个"轻量异步连接池"，没有这些配置：
  - 池满时 `await self._queue.get()` 会**永久阻塞**（HikariCP 的话会抛 `SQLTransientConnectionException: Connection is not available`）；
  - 没有 `validationQuery`，PG 那边因为 idle 超时把连接关了，池里还以为连接活着，下次用就报错。

**当前状态**：本次重点是把 RAG 跑通，连接池**只动了 autocommit**这一项（见 B2）。剩下的 timeout / 健康检查留作下一轮治理（生产前必须做，建议直接换 `psycopg_pool.AsyncConnectionPool`）。

### B2. `autocommit=False` 导致 INSERT 静默丢失

**现象**：入库脚本日志说"已写入 86 文档 / 342 chunks"，但脚本退出后立刻去查库，`COUNT(*) = 0`。

**根因（Java 对照精确版）**：

```java
// 类比这段 Java 代码
Connection conn = dataSource.getConnection();
conn.setAutoCommit(false);
PreparedStatement stmt = conn.prepareStatement("INSERT ...");
stmt.executeUpdate();
// 注意：这里没有 conn.commit()
conn.close();   // 池归还，HikariCP 会 rollback 未提交事务
```

Python `psycopg` 的行为跟 JDBC 完全一致：**默认 autocommit=False，必须显式 commit 才落盘**。

我代码里 `insert_document` 直接 `await conn.execute(INSERT...)`，没包在事务里也没 commit；连接归还到池后，池在关闭连接时 rollback，写入消失。

**修复**：让连接池创建的连接**默认开启 autocommit**，由显式的事务块（类似 `try-with-resources` 里的 `conn.transaction()`）控制原子性：

```python
# @d:\companyCode\agent\src\xinyidai_agent\rag\storage.py:555-563
conn = await AsyncConnection.connect(
    self._dsn,
    row_factory=dict_row,
    autocommit=True,   # ← 关键
)
```

类比 Java：相当于 HikariCP 的连接默认 `autoCommit=true`；要做事务时用 `@Transactional` 或手动 `conn.setAutoCommit(false); ...; conn.commit()`。

### B3. `SET hnsw.ef_search = ?` 不能用参数占位符

**现象**：执行 RAG 检索报 `psycopg.errors.SyntaxError: syntax error at or near "$1"`。

**根因（MySQL 对照）**：
- PostgreSQL 的 `SET` 是配置语句，**不支持 prepared statement 参数化**；
- 类似 MySQL 的 `SET SESSION sql_mode = ?` 也不行，必须直接拼到 SQL 里。

**修复**：`ef_search` 字段已经在代码里被 `int()` 强制转型，不存在注入风险，直接拼字面量；并且用 `SET LOCAL`（事务级）避免污染连接池里的连接复用：

```python
# @d:\companyCode\agent\src\xinyidai_agent\rag\storage.py:248-254
async with conn.transaction():
    # SET 不支持参数协议；ef_search 已经是 int，直接拼接安全。
    await conn.execute(f"SET LOCAL hnsw.ef_search = {int(self._hnsw_ef_search)}")
    rows = await conn.execute(...)  # 实际查询
```

类比 MySQL：`SET LOCAL xxx = N` 等价于 `SET SESSION xxx = N` 但只在事务内有效，事务结束自动还原；HikariCP 拿回去复用时不受影响。

### B4. baseline 表 schema 与新版代码完全不兼容

**现象**：库里已有 baseline 留下的 `rag_chunks` 表（90 行），但列结构跟新版代码完全不同：

## 4. C 类：异步 / 事件循环问题（重点解释）

> 这一类是你最不熟的 Python 特性，我尽量讲清楚。

### 先讲清楚什么是 event loop

Python 的 `asyncio` 是**单线程异步模型**：

```text
线程 T  ┃  ┌───────── event loop ─────────┐
        ┃  │ task1 (RAG 检索 await DB)     │
        ┃  │ task2 (RAG 检索 await DB)     │
        ┃  │ task3 (HTTP 请求 await IO)    │  ← I/O 等待时切到下一个 task
        ┃  │ ...                          │
        ┃  └──────────────────────────────┘
```

跟你熟悉的 Java 类比：
- **Netty 的 `EventLoop`**：一个线程跑一个 `EventLoop`，里面挂多个 `Channel`，I/O 等待时让出；
- **Project Reactor / Vert.x**：响应式编程，所有阻塞操作必须切到专门的 worker 线程；
- **Java virtual thread (Loom)**：21 之后内置的"看起来像同步、底层非阻塞"。

`asyncio` ≈ Netty + Project Reactor，但更简洁。

### C1. Windows 默认的 Proactor event loop 与 psycopg 不兼容

**现象**：

```text
psycopg.InterfaceError: Psycopg cannot use the 'ProactorEventLoop' to run in async mode.
Please use a compatible event loop, for instance by setting
'asyncio.set_event_loop_policy(WindowsSelectorEventLoopPolicy())'
```

**根因（精确版）**：

`asyncio` 在不同操作系统下有两种实现：

| 类型 | 底层 | 平台 | 谁兼容 |
|---|---|---|---|
| `SelectorEventLoop` | epoll (Linux) / kqueue (Mac) / select | Linux/Mac 默认；Windows 也有 | psycopg async ✅ |
| `ProactorEventLoop` | Windows IOCP（异步完成端口） | **Windows 默认** | psycopg async ❌ |

`psycopg` 异步驱动用的 socket 操作只能在 `Selector` 风格下跑——这是 psycopg 的已知限制。

**类比 Java**：Netty 在 Linux 用 `EpollEventLoop`、在 Windows 用 `NioEventLoop`，平台差异是固有的。

**修复**：在所有创建 event loop 的地方强制 Selector：

```python
# @d:\companyCode\agent\src\xinyidai_agent\rag\async_runtime.py:26-34
def _create_event_loop() -> asyncio.AbstractEventLoop:
    if sys.platform.startswith("win"):
        return asyncio.SelectorEventLoop()  # 强制 Selector
    return asyncio.new_event_loop()
```

uvicorn 启动 FastAPI 时也加了同样的 policy 设置（`@d:\companyCode\agent\src\xinyidai_agent\api.py:38-44`）。

### C2. FastAPI sync handler + asyncio.run 的"跨 event loop" bug（⭐ 最严重）

**现象**：之前审查代码时就指出过的真 bug，本次必须解决。

**问题链路**：

```text
FastAPI handler 是 sync 函数 (def chat, 不是 async def chat)
   ↓ FastAPI 会把它丢到一个 thread pool 里跑
   ↓
RagSearchTool.execute() 也是 sync
   ↓
ProductionRAGRetriever.retrieve() sync 入口
   ↓ 内部调 asyncio.run(retrieve_async(...))   ← 关键
   ↓ asyncio.run 每次创建一个新的 event loop！
   ↓
PgVectorStore 的连接池（asyncio.Queue）是在另一个 loop 里创建的
   ↓
跨 loop 操作 asyncio.Queue → RuntimeError: got Future attached to a different loop
```

**Java 类比（精确）**：

```java
// 假设你有这样一段 Java 代码
EventLoopGroup group1 = new NioEventLoopGroup(1);
Channel channel = group1.register(...).channel();  // channel 绑定到 group1 的 loop

// 然后突然想在另一个线程里用这个 channel
EventLoopGroup group2 = new NioEventLoopGroup(1);
group2.execute(() -> channel.writeAndFlush("hello"));  // 💥 异常！
// 因为 Netty 的 channel 严格绑定到注册时的 EventLoop
```

asyncio.Queue / Future 也一样**严格绑定 loop**，跨 loop 用就炸。

**修复（生产级方案）**：用一个**长期常驻的后台线程跑独立 event loop**，所有协程都提交到它：

```python
# @d:\companyCode\agent\src\xinyidai_agent\rag\async_runtime.py:37-100
class AsyncRuntime:
    """后台线程 + 独占 event loop，对外提供同步 run_coroutine 接口。"""

    def __init__(self):
        self._loop = _create_event_loop()
        self._thread = threading.Thread(target=self._run, daemon=True)
        self._thread.start()
        # 等 loop 启动完成

    def run_coroutine(self, coro, timeout=None):
        # 把协程提交到后台 loop，同步等结果回来
        future = asyncio.run_coroutine_threadsafe(coro, self._loop)
        return future.result(timeout=timeout)

    def close(self):
        self._loop.call_soon_threadsafe(self._loop.stop)
        self._thread.join()
```

**Java 类比（这次完全可类比）**：相当于你专门开一条 Vert.x verticle 或 Reactor `Schedulers.boundedElastic()`，所有需要异步执行的请求都通过 `submit()` 提交到这条线程上的 EventLoop，外部多线程并发提交也安全。

效果：
- 连接池在这条 loop 里创建一次，所有请求复用；
- FastAPI sync handler 通过 `runtime.run_coroutine(retriever.retrieve_async(...))` 把协程推到后台 loop，自己阻塞等结果；
- 多个并发 HTTP 请求同时进来时，sync handler 各自在 thread pool 里阻塞等，但后台 loop 内部可以并发跑多个协程（I/O 等待时切换）——和 Java 后端用阻塞的 servlet handler + 异步 JDBC 是一个套路。

### C3. AsyncRuntime 内部创建 loop 时也要选 Selector（C1 的子问题）

完整 prompt 见 `@d:\companyCode\agent\src\xinyidai_agent\router\model_router.py:40-90`。

### D2. 同 scene 多 capability 时 resolver 无法区分

**现象**：拉直边界后，DATA_QUERY 下出现两个 capability：

| capability | 处理范围 | 工具 |
|---|---|---|
| `credit.limit.read` | 企业维度（企业授信额度、风险标签等） | `query_credit_amount` |
| `product.terms.read` | 产品维度（利率、额度区间、期限） | `query_product_terms`（**未注册**，对接业务方 Java 后端） |

但 `CapabilityResolver` 原来只按 scene 派生，scene 有多个 capability 时直接退化成 ambiguous → 转 unknown.clarify 追问。

**修复**：升级 resolver 匹配优先级（`@d:\companyCode\agent\src\xinyidai_agent\capabilities\resolver.py:27-98`）：

```text
优先级 1. 按 raw_intent 在该 scene 候选中**精确命中**（catalog 配的别名）
优先级 2. 按 raw_intent_keywords **子串模糊命中**（命中数严格最多者）
优先级 3. scene 唯一候选 → scene_default
优先级 4. scene 无候选 → 跨 scene 别名兜底
优先级 5. 都不行 → ambiguous，追问
```

类比：相当于 Spring `@RequestMapping` 的多匹配规则——精确路径优先于通配符路径优先于默认路径。

### D3. raw_intent 别名词典必须够全

**现象**：模型输出 `raw_intent=query_product_quota`，catalog 里没列这个别名，匹配不上。

**修复**：双管齐下：

1. **catalog 别名表加常见近义词**（`@d:\companyCode\agent\src\xinyidai_agent\capabilities\catalog.py`）：
   - `product.terms.read.raw_intent_aliases` 列了 18 个别名（rate / interest_rate / quota / amount / term / period / fee 各种说法）；
   - `knowledge.policy.read.raw_intent_aliases` 列了 13 个。

2. **新增 `raw_intent_keywords` 字段做子串兜底**（`@d:\companyCode\agent\src\xinyidai_agent\capabilities\base.py:20`）：
   - 即使 raw_intent 是个新词（如 `query_product_quota_range`），只要包含 `product` + `quota` 这种关键词，就能命中 `product.terms.read`；
   - 算法是"命中关键词数严格最多的那个 capability 胜出"，避免歧义。

**最终诊断结果**（脚本 `@d:\companyCode\agent\scripts\diag_intent_router.py`）：9 条 query 全部正确分流，包括各种边界 case。

## 6. E 类：测试方法问题

### E1. PowerShell `Invoke-RestMethod` 编码乱码导致假 LOW_CONFIDENCE

**现象**：每次用 PowerShell 调 `/chat`，都返回 `LOW_CONFIDENCE / unknown.clarify`，但用 Python 直接调路由器又是正确的 `KNOWLEDGE_QA + 0.95`。

**根因**：

| 客户端 | body 编码 | 服务端解析 | 结果 |
|---|---|---|---|
| PowerShell `Invoke-RestMethod` | 默认按系统代码页（中文 Windows = GBK） | UTF-8 | 中文变乱码 |
| Python `urllib.request` | 显式 `body.encode("utf-8")` | UTF-8 | ✅ |

服务端读到乱码后，`RuleBasedRouter._is_low_information` 用正则 `re.fullmatch(r"[\W\d_]+", ...)` 判定为"全非字母字符"（因为乱码字节都不在 `\w` 里），直接返回 `unknown_route(confidence=0.2)` —— 根本没走模型识别。

**修复**：写了 `@d:\companyCode\agent\scripts\smoke_chat_endpoint.py` 用 Python urllib 强制 UTF-8 测试。

**经验值**：以后所有"中文 query 测试"都不要用 PowerShell `Invoke-RestMethod` 直接发；要么用 `curl --data @file.json`、要么用 Python。

类比：你做 Java 后端时如果用 IE 浏览器测带中文的 form 表单也会遇到同样的事，需要强制 `request.setCharacterEncoding("UTF-8")`。

## 7. F 类：已识别未修的 P1（待办）

### F1. 工具未注册时 Agent 编造"已调用工具"的幻觉

**现象**：query "小微税贷的利率是多少" 路由结果正确（DATA_QUERY → product.terms.read → `query_product_terms`），但因为这个工具没在 ToolRegistry 注册，Agent 没有真调用，**模型却自己编了一段"正在为您查询..."的回复**。

```text
route.should_call_tool = True
tool_trace = []                    ← 实际没调
business_status = NO_TOOL_USED
answer = "我将为您查询知识库中关于'小微税贷'的利率相关政策。正在检索……"  ← 幻觉
```

**风险**：用户以为查询发起了，实际什么都没发生。

**修复方向**（暂未实施，约 10 分钟工作量）：
- `ControlledAgentLoop` 在拿不到工具时**强制走"工具未接入"的 user_visible_message**；
- 不允许模型自由生成；
- 业务侧应该返回"该功能正在对接中"的明确提示。

类比 Java：相当于 Spring `@Controller` 的方法找不到对应 `@Service` Bean 时不应让模板引擎随便渲染，应该 fail-fast 到 503。
